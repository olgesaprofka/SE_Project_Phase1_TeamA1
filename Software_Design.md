# Phase III: Software Design and Modeling
## Kindergarten Child Management System


## 1. Software Architecture

### System Architecture

The Kindergarten Child Management System follows a **three-tier architecture** consisting of a Presentation Layer (Frontend), an Application Layer (Backend), and a Data Layer (Database).

The flow of the system works as follows:

- **Parent / Teacher / Admin** interacts with the system through the web-based Frontend (HTML, CSS, JavaScript)
- The request is sent to the **Backend** (Python – Flask Framework) via HTTP/API calls
- The Backend checks the **Database** (MySQL) — verifies user credentials, retrieves child records, attendance logs, activity reports, or messages
- The Backend processes the request and sends the result back to the **Frontend**
- The user confirms the action (e.g. submitting attendance, sending a message) and the result is stored in the Database

## 2. Detailed Design

### Class Diagram

> 📌 *Diagram file:* `02_Class_Diagram.png`

![Class Diagram](02_Class_Diagram.png)

The class diagram shows all main classes of the system, their attributes (with visibility and data type), their methods, and how they relate to each other. All classes are derived directly from the database entities defined in Phase II.

**Classes and their roles:**

| Class | Role |
|---|---|
| User | All system users (parent, teacher, admin) — handles login, logout, password reset |
| Child | Child profile with personal, medical, and emergency contact data |
| AttendanceRecord | Records check-in/check-out per child per day with automatic timestamp |
| ParentChildRelationship | Associative class linking parents to children (many-to-many relationship) |
| ActivityReport | Daily activity reports created by teachers for each child |
| Message | Messages exchanged between parents and teachers |
| Notification | System-generated alerts sent to users (e.g. attendance notifications) |
| Report | Exportable attendance and progress reports generated by admin |

**Relationships and multiplicities:**

- A **User** can be linked to **0..*** children through ParentChildRelationship (`linked to`)
- A **Child** can have **0..*** AttendanceRecords (`has`)
- A **User** (Teacher) **records** **0..*** AttendanceRecords
- A **Child** can have **0..*** ActivityReports (`has`)
- A **User** (Teacher) **creates** **0..*** ActivityReports
- A **User** **sends** **0..*** Messages
- A **User** **receives** **0..*** Notifications
- A **User** (Admin) **generates** **0..*** Reports

### Sequence Diagrams

#### Sequence Diagram 1 — Attendance Recording

> 📌 *Diagram file:* `03_Sequence_Diagram_Attendance.png`

![Sequence Diagram 1 - Attendance](03_Sequence_Diagram_Attendance.png)

This diagram illustrates the step-by-step process of a teacher recording a child's attendance:

1. Teacher selects a child and marks attendance on the Frontend
2. Frontend sends a `POST /attendance` request to the Backend
3. Backend validates that the child exists in the Database
4. Database returns the child record to the Backend
5. Backend saves the attendance record with an automatic timestamp to the Database
6. Backend logs a notification entry for the parent in the Database
7. Backend confirms the action to the Frontend
8. Frontend shows a success message to the Teacher
9. Backend sends a real-time attendance notification to the Parent

---

#### Sequence Diagram 2 — Parent–Teacher Messaging

> 📌 *Diagram file:* `04_Sequence_Diagram_Messaging.png`

![Sequence Diagram 2 - Messaging](04_Sequence_Diagram_Messaging.png)

This diagram illustrates the messaging flow between a parent and a teacher:

1. Parent opens the messaging screen on the Frontend
2. Frontend sends `GET /messages` to the Backend
3. Backend fetches the conversation history from the Database
4. Database returns messages to the Backend, which forwards them to the Frontend
5. Frontend displays the conversation to the Parent
6. Parent types and sends a message — Frontend sends `POST /messages` to the Backend
7. Backend stores the message in the Database
8. Backend sends a new message notification to the Teacher
9. Backend confirms delivery to the Frontend
10. Teacher receives the notification and reads the message

---

#### Sequence Diagram 3 — User Login and Authentication

> 📌 *Diagram file:* `05_Sequence_Diagram_Login.png`

![Sequence Diagram 3 - Login](05_Sequence_Diagram_Login.png)

This diagram illustrates the login and authentication process with two alternative flows:

1. User enters email and password on the Frontend
2. Frontend sends `POST /login` with credentials to the Backend
3. Backend fetches the user record from the Database by email
4. Backend verifies the password hash internally

**[Success] Valid credentials:**
- Backend creates a session token and stores it in the Database
- Backend returns the token and user role to the Frontend
- Frontend redirects the user to their role-specific dashboard

**[Fail] Invalid credentials:**
- Backend returns `401 Unauthorized` to the Frontend
- Frontend displays an error message to the User

### Activity Diagrams

#### Activity Diagram 1 — Record Attendance

> 📌 *Diagram file:* `07_Activity_Diagram_Attendance.png`

![Activity Diagram 1 - Attendance](07_Activity_Diagram_Attendance.png)

This flowchart describes the full process of recording attendance for all children:

1. Teacher logs into the system
2. Teacher opens the attendance list
3. Teacher selects a child from the list
4. **Decision:** Is the child present?
   - **Yes →** Mark as Present
   - **No →** Mark as Absent
5. System automatically timestamps the attendance record
6. System saves the record to the database
7. **Decision:** Have all children been recorded?
   - **No →** Loop back to select the next child
   - **Yes →** Continue
8. System sends attendance notifications to all parents
9. System shows a confirmation message to the Teacher

#### Activity Diagram 2 — Parent Views Activity Report

> 📌 *Diagram file:* `08_Activity_Diagram_Parent_Report.png`

![Activity Diagram 2 - Parent Report](08_Activity_Diagram_Parent_Report.png)

This flowchart describes the process of a parent accessing their child's activity report:

1. Parent opens the app and enters login credentials

   - **No →** Show error message → loop back to login
   - **Yes →** Redirect to parent dashboard

4. Parent clicks "Activity Reports"
5. System fetches reports from the database
6. **Decision:** Are reports available?
   - **No →** Show empty state message
   - **Yes →** Display the list of activity reports
7. Parent selects a specific report to view
8. System displays the full report details
9. Parent has the option to download the report

### State Diagrams

#### State Diagram 1 — Attendance Record

> 📌 *Diagram file:* `09_State_Diagram_Attendance.png`

![State Diagram 1 - Attendance](09_State_Diagram_Attendance.png)

This diagram illustrates the different states an attendance record can be in:

| State | Description |
|---|---|
| Not Recorded | Initial state — no attendance has been logged for the child yet |
| Checked In | The child has been marked as present and check-in time is recorded |
| Checked Out | The child has left and check-out time is recorded |
| Absent | Triggered automatically if no check-in is recorded before a set time |

**Transitions:**
- `check-in` → Not Recorded becomes Checked In
- `check-out` → Checked In becomes Checked Out
- `timed out` → Not Recorded becomes Absent (automatic)
- `assign to next day` → Checked Out resets to Not Recorded for the next session

#### State Diagram 2 — Message

> 📌 *Diagram file:* `10_State_Diagram_Message.png`

![State Diagram 2 - Message](10_State_Diagram_Message.png)

This diagram illustrates the lifecycle of a message within the messaging system:

| State | Description |
|---|---|
| Composed | The message has been written but not yet sent |
| Sent | The message has been submitted by the sender |
| Delivered | The message has successfully reached the recipient's inbox |
| Read | The recipient has opened and read the message |
| Failed | Delivery failed due to a system or network error |

**Transitions:**
- `send` → Composed becomes Sent
- `delivered` → Sent becomes Delivered
- `read` → Delivered becomes Read
- `failed` → Sent becomes Failed
- `retry` → Failed goes back to Sent

---

#### State Diagram 3 — User Account

> 📌 *Diagram file:* `11_State_Diagram_User_Account.png`

![State Diagram 3 - User Account](11_State_Diagram_User_Account.png)

This diagram illustrates the different states a user account can go through in the system:

| State | Description |
|---|---|
| Pending | Account has been registered and is awaiting admin approval |
| Active | Account has been approved and the user can fully access the system |
| Inactive | Account has been deactivated by the admin (temporarily disabled) |
| Locked | Account has been locked due to multiple failed login attempts |
| Rejected | Account registration has been denied by the admin |

**Transitions:**
- `approve` → Pending becomes Active
- `reject` → Pending becomes Rejected
- `deactivate` → Active becomes Inactive
- `reactivate` → Inactive returns to Active
- `lock` → Active becomes Locked (after failed login attempts)
- `unlock` → Locked returns to Active
- `delete` → Active is permanently removed from the system
